## 4. Live signal check — corrected after finding a test-pollution bug

**Correction:** the first draft of this report counted `fundamental_signals` rows for 07-06/07/09/10 (6, 23, 6, 18 respectively) as real screener output. They weren't. `tests/test_orchestrator.py` was writing fake rows (`ticker='MSFT', composite_score=80, rationale='good'`) straight into the live `trading.db` on every `pytest` run, because `_process_fundamental_candidate`'s `insert_fundamental_signal` call (`orchestration/main_loop.py:1163`) used a local (function-scoped) import that bypassed the module-level `mocker.patch(...)` pattern the rest of the test file uses — 287 of the table's 289 rows were this leaked test fixture data. Root-caused, fixed (import moved to module level; both `orch`/`orch_fitted` fixtures now mock it, matching the existing `record_job_run` mock precedent), full suite reconfirmed green (877 passed, 1 pre-existing unrelated failure), and the 287 fake rows deleted from the live DB. This did **not** affect real trading — `self._portfolio` is a mock in those same tests, so no fake position/order was ever placed; only the signal audit-trail table was corrupted.

**Real picture, after cleanup:** `fundamental_signals` has exactly 2 rows — CF and VTRS, both 07-07, both the already-documented phantom-position trades (approved by AI scoring, but never filled due to the `OrderStatus.FILLED` bug, fixed same day). **No real fundamental candidate has been generated on 07-06, 07-08, 07-09, or 07-10** — consistent with the separately-diagnosed in-memory-scheduler-dropping-days bug (fixed today, commit `0d93f8b`, 12:36 CEST). `positions` is empty and `closed_positions` has one `'test'`-tagged fixture row from January — real facts, unaffected by the pollution bug (this table was never touched by it).

**Today's fix is not yet live-tested.** The scheduler fix landed at 12:36 CEST; the current bot process (PID 20132) started at 12:46 CEST (after the fix) and has so far only run `run_screener_prefetch` (13:00, completed normally). `run_morning_pipeline` — the first real end-to-end test of whether a candidate can now reach a filled position — is scheduled for 14:00 CEST and had not run as of this report (13:2x CEST). `launchctl list` shows no loaded job either — the launchd plist from the 07-10 fix was never loaded; a manual process is running instead. Whether the bot actually produces a real position today is still an open, testable question, not yet answered.

**Known limitation restated:** even once positions start opening again, `fundamental_signals.composite_score` is the only persisted score — no per-sleeve attribution exists in the schema, so live sleeve-level performance will only ever be inferable via the backtest refresh (section 3), not measured directly.
